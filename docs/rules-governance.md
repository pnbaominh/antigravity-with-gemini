# Technical Governance Framework: RULES.MD

The **RULES.MD Technical Governance Framework** provides a deterministic contract for architectural synthesis. It ensures that plans generated by Gemini and executed by Antigravity meet production engineering standards rather than vague, hallucinated "vibe-coding" steps.

---

## 1. The 5 Fundamental Axioms

Every plan synthesized by G2A must satisfy five immutable axioms:

### Axiom 1: AS-IS Reality Grounding
- Plans must be anchored in the current codebase state.
- Hallucinating non-existent libraries, unsupported runtime versions, or uninstalled tools is strictly prohibited.
- Pre-planning reconnaissance must inspect `package.json`, configuration files, and existing source directories before blueprint formulation.

### Axiom 2: Strict Scope Boundaries (Non-Goals \(\ge 3\))
- Every plan must explicitly enumerate at least **3 directly related items that are decisively OUT OF SCOPE**.
- Each Non-Goal must include a clear technical justification explaining why it is excluded from the current initiative.
- This prevents scope creep and protects Antigravity from getting derailed by tangential refactors.

### Axiom 3: Single Directly Responsible Individual (Single DRI)
- Every task within the Work Breakdown Structure must have exactly **one accountable DRI** (e.g., `DRI: lead_architect`).
- Shared ownership (`DRI: team`) or unassigned tasks are prohibited.

### Axiom 4: Quantitative PERT Estimation
- Durations must not be guessed as single vague numbers.
- Each phase must calculate a 3-point PERT estimation:
  $$\text{Expected Duration: } E = \frac{O + 4M + P}{6}$$
  $$\text{Standard Deviation: } \sigma = \frac{P - O}{6}$$
  where:
  - \(O\) = Optimistic estimate (best-case scenario in hours)
  - \(M\) = Most likely estimate (normal scenario in hours)
  - \(P\) = Pessimistic estimate (worst-case scenario with blocks in hours)

### Axiom 5: Binary Definition of Done (DoD)
- Acceptance criteria must be binary (Pass/Fail) with zero room for subjective interpretation.
- "Code looks clean" or "App should work" is prohibited.
- Criteria must be runnable: `100% automated tests PASS`, `tsc --noEmit clean (0 errors)`, `clean build (npm run build exit 0)`.

## 2. The 6 Mandatory Sections

Every valid implementation plan must be structured into the following 6 sections:

### Section 1: AS-IS State & System Architecture Blueprint
1. **System Overview & Tech Stack**: Complete list of runtimes, frameworks, testing libraries, and native APIs with technical rationales.
2. **Architecture & Data Flow Diagram**: Visualized as a Mermaid flowchart (`flowchart TD`) showing component relationships, state transitions, and data movement.
3. **Directory & File Layout**: Explicit inventory of files marked with atomic action tags:
   - `[NEW]`: New files to create.
   - `[MODIFY]`: Existing files to edit.
   - `[DELETE]`: Deprecated files to remove.
4. **Core TypeScript Interfaces & Data Contracts**: Complete type signatures and data models written out with full type declarations.

### Section 2: Non-Goals & Scope Boundaries (Mandatory \(\ge 3\))
A numbered list of at least 3 related topics that will NOT be touched in this sprint:
```markdown
## 2. Non-Goals & Scope Boundaries
1. Database Schema Migration: Out of scope because existing tables support the new fields.
2. Web UI Dashboard: Out of scope; CLI and REST endpoints are sufficient for Phase 1.
3. Multi-Region Replication: Out of scope to avoid premature complexity.
```

### Section 3: Unknowns & Halt Checks
- Explicitly declares whether critical technical unknowns or blocker questions exist.
- If all prerequisites are resolved: `Status: CLEAR`.
- If critical dependencies or API access keys are missing: `Status: HALT` with required empirical tests.

### Section 4: Risk Assessment & RAID Log (Mandatory \(\ge 4\) entries)
A Pre-Mortem risk matrix identifying potential failure modes before any code is written:
| ID | Category | Description | Impact | Likelihood | Mitigation Strategy | Owner DRI |
|---|---|---|---|---|---|---|
| R-1 | Risk | Concurrency race condition | High | Medium | Defensive mutex lock / debounce | lead_architect |
| R-2 | Risk | Windows CRLF vs POSIX paths | Medium | High | Normalized path utilities | lead_architect |
| R-3 | Risk | Network API timeout | High | Low | Exponential backoff with jitter | lead_architect |
| A-1 | Assumption | Node.js runtime >= 18 | Medium | Low | Runtime version check on startup | lead_architect |

### Section 5: Work Breakdown Structure (WBS) & Phased Implementation
- Sequenced into atomic phases adhering to the 8/80 rule (minimum 8 hours, maximum 80 hours total scope).
- Every phase must contain:
  1. Phased title (e.g., `### Phase 1: Foundation & Types`).
  2. Granular task checkboxes (`- [ ] Task 1.1: ...`) with file tags (`[NEW]`, `[MODIFY]`).
  3. **Runnable Shell Verification Command**: Concrete command that can be executed directly in the terminal to verify the phase (e.g., `npm.cmd test tests/auth.test.ts` or `npx tsc --noEmit`).
  4. 3-point PERT estimation: `PERT: O=2h, M=4h, P=8h, E=4.33h, Sigma=1h`.

### Section 6: Definition of Done & Quality Gates
Binary pass/fail criteria:
- [ ] 100% automated unit and integration tests pass
- [ ] Zero TypeScript compilation errors (`tsc --noEmit`)
- [ ] Zero ESLint / linter warnings
- [ ] Clean production build (`npm run build`)
- [ ] All new files contain technical documentation headers

---

## 3. Programmatic Governance Engine (`RulesEngine`)

G2A enforces these standards automatically via `src/governance/rules-engine.ts`:
- **Validation**: Invoked automatically during plan audits or manually via the MCP tool `gemini_validate_plan`.
- **Score Calculation**: Plans missing sections or failing axioms receive score deductions. If the score is < 90, G2A triggers an autonomous in-thread refinement loop to correct the deficiencies.
